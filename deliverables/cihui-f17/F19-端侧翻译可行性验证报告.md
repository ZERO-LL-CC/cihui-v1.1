# F19 端侧离线翻译可行性验证报告（方案 A）

> 验证目标：把 `cihui-translate-demo` 里跑通的 Opus-MT（zh→en）真正搬进鸿蒙 App，实现「真翻译、断网可用」。
> 结论：**技术链路已完全打通且译文正确，但内存代价 906MB，在目标设备上必然被系统回收，当前形态不可用。**
> 验证日期：2026-10-22　设备：HarmonyOS 6.1.1(24) / 7.8GB RAM

---

## 1. 结论先行

| 维度 | 结果 |
|---|---|
| 能否真翻译 | **能**。`为什么不能翻译` → `Why can't you translate it?` |
| 是否真离线 | **是**。全程无网络请求，资源全部来自 rawfile |
| 加载耗时 | **3.1s**（109MB 模型） |
| 单句推理 | **5.7s**（20 字中文） |
| 包体增量 | 8.4MB → **141MB（+132MB）** |
| 主进程内存 | 219MB |
| **渲染进程内存** | **687MB** |
| **存活时长** | **约 19 秒后系统 SIGKILL** |

判定：**当前形态否决**。不是「代码写错了」，是「这台设备扛不住 687MB 的 Web 渲染进程」。

被杀的硬证据：

```
20:50:37 AppMS: kill pid 63332, ret:0, Kill Reason:KillRenderProcess
20:50:37 appspawn: com.cihui.word with pid 63332 exit with signal:9
```

## 2. 完整内存曲线（每 2 秒采样）

| 时刻 | 主进程 | 渲染进程 | 备注 |
|---|---|---|---|
| 2s | 214MB | 343MB | 页面加载 |
| 4s | 215MB | **656MB** | 模型开始进 wasm 堆 |
| 8s | 214MB | 677MB | 推理中 |
| 13s | 216MB | ~687MB | 推理完成、已执行 `dispose()` |
| 20s | 219MB | 687MB | **释放后不回退** |
| 22s | — | — | **进程消失** |

关键点：`translator.dispose()` 生效后 JS 堆从 ~600MB 降到 **150MB**，
但**渲染进程 RSS 停在 687MB 不动**。原因是 WebAssembly 的线性内存只能增长、
无法归还给操作系统（`memory.grow` 没有反向操作），加上 Chromium 渲染进程本身
约 150–200MB 基线。所以「用完就释放」这个优化在此方案下**救不回来**。

## 3. 打通的三个技术关卡（复用价值高）

这三点是本次验证最值钱的部分，后续任何走 Web + wasm 的方案都会遇到。

### 3.1 `resource://rawfile/` 下不能用 ES Module

现象：`Failed to fetch dynamically imported module: resource://rawfile/mt/js/transformers.min.js`

原因：`resource://` 的 Origin 是 `null`，ESM 加载强制要求 CORS，直接被拒。

解法：把 webpack 产出的 ESM bundle 转成 IIFE，挂到 `window`。
transformers.js 的 dist 末尾是一条 `export{a as b, c as d, ...}`（501 项），
用脚本转成 `window.transformers={b:a, d:c, ...}` 并整体包一层 IIFE，避免污染全局。
转换后 `node --check` 通过，`pipeline` / `env` / `AutoTokenizer` 均在。

### 3.2 `resource://rawfile/` 下 fetch 全部失败

现象：`config.json=ERR:Failed to fetch`，四个文件无一例外。
`<script src>` 能加载（no-cors），但 `fetch()` 不行——该 scheme 不在 fetch 支持的协议内。

解法：**伪造 https 源 + `onInterceptRequest` 拦截**。
- 页面 src 用 `https://mt.local/index.html`
- ArkTS 侧拦截该域全部请求，映射回 rawfile
- `setResponseData(Resource)` 直接传 `$rawfile()` 的对象，系统流式读取，
  **不必先把 109MB 读进内存再拷贝**（这点很关键，否则内存还得再翻一倍）

注意：`$rawfile()` 只接受编译期字面量，所以拦截时必须**逐个 case 枚举文件**，
不能用字符串拼接。实测 11 个文件，可接受。

### 3.3 其余两个小坑

- transformers.js 找模型的实际路径是 `models/<org>/<name>/onnx/*.onnx`，
  少一层 `onnx/` 目录会报 `file was not found locally`。
- wasm 的 Content-Type 必须是 `application/wasm`，否则 `instantiateStreaming` 失败。

## 4. 为什么这么贵：687MB 是哪来的

| 来源 | 估算 |
|---|---|
| Chromium 渲染进程基线 | 150–200MB |
| encoder 51MB + decoder 58MB onnx 解码后的权重 | ~110MB |
| onnxruntime wasm 线性内存（只增不减） | ~250MB |
| tokenizer.json 6MB + vocabulary | ~30MB |
| 推理时激活张量 / KV cache | ~100MB |

合计 ≈ 690MB，与实测 687MB 吻合。

对比：目标设备总内存 7.8GB，实测可用常在 300–800MB 之间（此前 R-06 已确认
系统同时在回收 `FusionSearch`、应用市场等）。**687MB 的单进程申请量必然触发回收。**

## 5. 三条后续路径（按性价比排序）

### A1. 换更小模型（推荐先试）

目标：把模型从 109MB 压到 **20–30MB**，让渲染进程落在 250MB 以内。

可选：
- `opus-mt-zh-en` 的更激进量化（int8 → 已是 quantized，可试 4-bit）
- 换蒸馏版小模型（如 TinyBERT 级 encoder + 小 decoder）
- 或先只做「中文→英文关键词」而非整句，用小得多的分类式模型

代价：翻译质量会下降；包体约 +30–40MB。
工作量：需要重新找模型 + 转换 + 验证，半天到一天。

### A2. 走鸿蒙原生 onnxruntime（不走 Web）

省掉 Chromium 的 150–200MB 基线和 wasm 线性内存的浪费。
但需要：onnxruntime 的鸿蒙原生库（NDK 编译或找三方产物）+ ArkTS NAPI 封装 + 分词器移植。
代价：技术风险最高，工作量 3–5 天，且能否拿到可用库不确定。

### A3. 放弃端侧，改用云端大模型

一句约 100 token，成本可忽略，包体不变，译文质量远高于 Opus-MT。
代价：必须联网、需要 Key。
注：`SentenceGeneratorService` 里豆包客户端现成（超时/重试/错误码齐全），
加一个 `translate()` 方法即可，**半小时能上**。

**我的建议：A3 先上（解当下体验），A1 作为技术储备并行验证。A2 不建议。**

```

                 ... 'isTodayBatchBrowsed' / 'browseResumeAt'
```

排查结果：
- `viewmodel/StudyEntry.ets` 已切到 `StudySessionStore` 新会话架构（+156/−50），
  导出换成了无参的 `entryLabel()`
- 但 `pages/tab/HomePage.ets` 仍是旧版本，还在 import 那三个旧 API
- 另有新增未跟踪文件 `service/StudySessionStore.ets`
